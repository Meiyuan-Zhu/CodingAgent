# ADR-0002：决策与开发记录分开维护

- 日期：2026-08-27
- 状态：accepted
- 确认来源：用户明确要求决策放入 decisions/，开发文档及后续实现状态放入 memory/。
- 实现状态：文档结构已建立，文档核验见 DOC-001；不代表应用已实现。

## 问题与约束

项目由 AI 辅助实现，用户需要理解设计取舍并在后续开发与面试中追踪实际进展。仅依赖聊天会分散信息；将计划与完成情况混写容易误报能力。

## 备选方案

1. 所有内容写入单个方案文件：入口简单，但当前状态与历史建议容易混淆。
2. 决策与状态都放在 docs/：可以工作，但不符合用户明确提出的目录组织偏好。
3. decisions/ 记录理由，memory/ 记录方案与开发事实：采用；需维护链接并避免重复状态表。

## 决定与维护约定

- decisions/：ADR、编号索引和模板，记录当时的理由、备选与取代关系。
- memory/PROJECT_PLAN.md：总体方案和范围，不作为完成报告。
- memory/STATUS.md：当前状态的唯一汇总，列出已实现、未验证、待实现和下一步。
- memory/DEVLOG.md：按阶段追加实际发生的变化，不补造历史。
- memory/VERIFICATION.md：记录检查范围、方法、结果与限制，不存未经脱敏的原始运行日志。
- memory/README.md：入口与文档职责；后续确需接口合同或面试材料时再增加文档，不先造空文档。
- AGENTS.md：后续开发入口和可维护性、验证、记录更新约定。
- `memory/` 不是产品运行时的模型上下文，不自动把开发记录发送给模型。

上述目录选择来自用户要求；具体文件划分和更新约定是本次落实方式，不声称用户逐条指定过这些细节。

## 代价与限制

记录需要随实现维护。通过单一状态汇总和证据链接降低重复；不要求每个小改动都新增 ADR。文件可追踪不等于已有 Git 历史，也不能代替实际代码审核和用户理解。

## 实现与验证证据

- 入口：[开发记录](../memory/README.md)、[开发约定](../AGENTS.md)。
- 当前状态：[STATUS.md](../memory/STATUS.md)。
- 文档验证：[VERIFICATION.md](../memory/VERIFICATION.md) 中的 DOC-001。
- 关联提交：尚无，当前未初始化 Git 仓库。

## 何时重新考虑

当记录重复、检索成本明显上升或协作方式改变时调整；以实际需求为依据，不因文件数量少而增加文档。
